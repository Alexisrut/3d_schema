# Развёртывание на сервере компании

Пошаговая инструкция. Всё запускается в Docker, поэтому порядок действий
одинаков для Ubuntu, Debian, RHEL/Rocky/Alma и Windows Server — различается
только установка самого Docker (шаг 1).

Ориентировочное время: **30–40 минут**, если сервер уже есть и к нему есть
доступ.

---

## Что получится

```
                 сервер компании
   ┌──────────────────────────────────────────────┐
   │                                              │
   │   ┌────────────┐        ┌────────────────┐   │
 ──┼──▶│    web     │───────▶│      api       │   │
80 │   │   nginx    │  внутр.│ FastAPI+uvicorn│   │
   │   │            │  сеть  │                │   │
   │   │ • фронтенд │        │ • база         │   │
   │   │ • /api  ──▶│        │ • модели .glb  │   │
   │   │ • /media▶  │        │ • вложения     │   │
   │   │ • /ws   ──▶│        └───────┬────────┘   │
   │   └────────────┘                │            │
   │                                 ▼            │
   │                          ./data (на диске)   │
   └──────────────────────────────────────────────┘
```

Два контейнера. Наружу открыт **только** `web` — бэкенд доступен лишь через
nginx. База и загруженные модели лежат в каталоге `./data` на диске сервера и
переживают любое обновление.

**Почему фронтенд и API на одном адресе.** Клиент обращается к API
относительными путями (`/api/...`), а адрес WebSocket собирает из адреса
страницы. Разнести их по разным хостам — значит настраивать CORS и всё равно
получить неработающие обновления в реальном времени.

---

## Требования к серверу

| | Минимум | Комфортно |
| --- | --- | --- |
| CPU | 2 ядра | 4 ядра |
| Память | 2 ГБ | 4 ГБ |
| Диск | 20 ГБ | 50 ГБ и больше |
| ОС | любая с Docker | Ubuntu 22.04/24.04 LTS |

Про диск: одна выгрузка из Revit — это десятки мегабайт (в проекте уже есть
модель на 36 МБ), предел на файл — 512 МБ. Считайте по числу проектов и слоёв
с запасом.

Нужен доступ по SSH (или RDP для Windows) и права администратора.

---

## Шаг 1. Установить Docker

**Ubuntu / Debian:**

```bash
curl -fsSL https://get.docker.com | sudo sh
```

**RHEL / Rocky / Alma:**

```bash
sudo dnf install -y dnf-plugins-core
sudo dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo systemctl enable --now docker
```

**Windows Server:** установите Docker Desktop либо Docker Engine с WSL2 —
дальнейшие команды выполняются в PowerShell без `sudo`.

Проверка:

```bash
docker --version && docker compose version
```

Чтобы не писать `sudo` перед каждой командой (Linux):

```bash
sudo usermod -aG docker $USER
```

После этого нужно перезайти в сессию SSH.

---

## Шаг 2. Положить код на сервер

```bash
sudo mkdir -p /opt/3d-monitoring
sudo chown $USER:$USER /opt/3d-monitoring
git clone <адрес-вашего-репозитория> /opt/3d-monitoring
cd /opt/3d-monitoring
```

Если репозитория нет — скопируйте папку проекта любым способом (`scp`, архив),
но **без** `node_modules`, `.venv`, `data.db` и `backend/storage`: это сотни
мегабайт, которые всё равно пересоберутся или создадутся заново.

---

## Шаг 3. Настройки

```bash
cp backend/.env.example backend/.env
```

Откройте `backend/.env` и заполните. Обязательные три строки:

```bash
# 1. Ключ подписи токенов входа. Сгенерировать:
#    docker run --rm python:3.12-slim python -c "import secrets; print(secrets.token_urlsafe(48))"
APP_SECRET_KEY=<сюда длинную случайную строку>

# 2. Пароль первого администратора (создастся при первом запуске)
APP_SEED_ADMIN_USERNAME=admin
APP_SEED_ADMIN_PASSWORD=<свой пароль>

# 3. Адрес, по которому люди открывают систему — попадёт в ссылки в письмах
APP_PUBLIC_BASE_URL=http://<IP-или-имя-сервера>
```

Почта уже настроена на Mail.ru (`APP_SMTP_*`) — если ящик тот же, менять
ничего не нужно.

> **`backend/.env` не попадает в репозиторий** (он в `.gitignore`) и не
> попадает в образ (он в `.dockerignore`). Пароли остаются только на сервере.
> Ограничьте права: `chmod 600 backend/.env`.

---

## Шаг 4. Каталог данных и права

```bash
mkdir -p data
sudo chown -R 10001:10001 data
```

`10001` — идентификатор пользователя, под которым работает приложение внутри
контейнера. Оно намеренно запускается **не от root**, поэтому право на запись
в этот каталог нужно выдать явно. Пропустите шаг — контейнер упадёт с
`unable to open database file`.

На Windows этот шаг не нужен.

---

## Шаг 5. Запуск

```bash
docker compose up -d --build
```

Первая сборка занимает 3–7 минут: скачиваются образы Python и Node, ставятся
зависимости, собирается фронтенд. Дальнейшие запуски — секунды.

Проверить, что оба контейнера поднялись:

```bash
docker compose ps
```

Оба должны быть в состоянии `running`, у `api` — ещё и `healthy`.

---

## Шаг 6. Проверка

```bash
# 1. Отвечает ли API
curl http://localhost/api/health
# ожидается: {"status":"ok"}

# 2. Отдаётся ли фронтенд
curl -I http://localhost/
# ожидается: HTTP/1.1 200 OK
```

Затем откройте в браузере `http://<IP-сервера>` и войдите под администратором
из шага 3.

Проверьте вручную то, что зависит именно от развёртывания:

1. **Загрузка модели** — «+ Добавить .glb». Проверяет предел на размер файла
   в nginx и права на запись в `./data`.
2. **Обновления в реальном времени** — в шапке должно гореть «обновления в
   реальном времени», а не «резервный режим опроса». Проверяет проксирование
   WebSocket.
3. **Перезагрузка страницы проекта** (F5 на `/projects/1`) — должна открыться
   та же страница, а не «404». Проверяет SPA-fallback.
4. **Письмо** — «Личный кабинет» → привязать почту, дождаться кода.

Если что-то не так — смотрите раздел «Если что-то пошло не так».

---

## Шаг 7. Закрыть лишнее снаружи

Открыт должен быть только веб-порт:

```bash
# Ubuntu / Debian
sudo ufw allow 80/tcp
sudo ufw allow 22/tcp
sudo ufw enable

# RHEL / Rocky / Alma
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=ssh
sudo firewall-cmd --reload
```

Порт бэкенда (8000) наружу не публикуется вовсе — это уже сделано в
`docker-compose.yml`.

---

## Обновление до новой версии

```bash
cd /opt/3d-monitoring
git pull
docker compose up -d --build
```

База и загруженные модели не трогаются: они в `./data`. Правки схемы
применяются автоматически при старте (`app/migrate.py`), отдельных команд
запускать не нужно.

Откатиться на предыдущую версию:

```bash
git checkout <предыдущий-коммит>
docker compose up -d --build
```

> Откат кода не откатывает базу. Если новая версия добавила поля, старая их
> просто не увидит — данные не пострадают. Но перед крупным обновлением
> сделайте резервную копию (ниже).

---

## Резервное копирование

Копировать нужно ровно один каталог — `./data`. В нём и база, и все файлы.

**Разовая копия:**

```bash
cd /opt/3d-monitoring
docker compose stop api                    # чтобы база не менялась во время копирования
sudo tar czf ~/backup-$(date +%F).tar.gz data backend/.env
docker compose start api
```

**Ежедневно по расписанию** — создайте `/opt/3d-monitoring/backup.sh`:

```bash
#!/bin/bash
set -e
cd /opt/3d-monitoring
DEST=/var/backups/3d-monitoring
mkdir -p "$DEST"
docker compose stop api
tar czf "$DEST/backup-$(date +%F).tar.gz" data backend/.env
docker compose start api
# хранить копии за 14 дней
find "$DEST" -name 'backup-*.tar.gz' -mtime +14 -delete
```

```bash
chmod +x /opt/3d-monitoring/backup.sh
sudo crontab -e
# добавить строку — копия каждую ночь в 3:00:
0 3 * * * /opt/3d-monitoring/backup.sh
```

Простой на время копирования — секунды. Копировать базу SQLite «на живую»
нельзя: получится файл в промежуточном состоянии, который может не открыться.

**Восстановление:**

```bash
cd /opt/3d-monitoring
docker compose down
sudo rm -rf data
sudo tar xzf /var/backups/3d-monitoring/backup-2026-08-01.tar.gz
sudo chown -R 10001:10001 data
docker compose up -d
```

## HTTPS и доменное имя

Пока доступ по IP внутри сети — HTTP допустим. Как только система выйдет за
периметр или появится домен, HTTPS нужен обязательно: **сейчас логин и пароль
идут по сети открытым текстом**.

**Вариант А — внутренний домен, сертификат от УЦ компании.**

1. Получите у администраторов сертификат (`.crt`) и ключ (`.key`) на имя вида
   `monitoring.company.lan`.
2. Положите их в `deploy/certs/` рядом с `docker-compose.yml`.
3. В `docker-compose.yml` раскомментируйте монтирование `deploy/certs` и
   добавьте проброс порта `"443:443"`.
4. В `frontend/deploy/nginx.conf` добавьте второй блок `server` (443 с
   `ssl_certificate`) и в блоке на 80 порту поставьте редирект на HTTPS.
5. `docker compose up -d --build`.

**Вариант Б — публичный домен, Let's Encrypt.** Проще всего добавить
контейнер `caddy` или `traefik` перед `web`: они получают и продлевают
сертификат сами. Скажите — подготовлю готовый `docker-compose.yml` под ваш
домен.

После перехода на HTTPS обновите `APP_PUBLIC_BASE_URL` в `backend/.env` —
иначе ссылки в письмах останутся с `http://`. WebSocket переключится на `wss`
сам: протокол он берёт из адреса страницы.

## Если что-то пошло не так

Первым делом — журналы:

```bash
docker compose logs -f          # всё сразу
docker compose logs -f api      # только бэкенд
docker compose logs -f web      # только nginx
```

| Симптом | Причина и что делать |
| --- | --- |
| `unable to open database file` в логах `api` | Не выданы права на `./data`. Выполните `sudo chown -R 10001:10001 data` и `docker compose restart api`. |
| Сайт открывается, но всё «отваливается» с 502 | Бэкенд не поднялся. `docker compose logs api` — обычно ошибка в `backend/.env`. |
| В шапке «резервный режим опроса» вместо «обновления в реальном времени» | Не проходит WebSocket. Проверьте, что между браузером и сервером нет ещё одного прокси, который не пропускает `Upgrade`. |
| F5 на странице проекта даёт 404 | Не применился конфиг nginx. Пересоберите `web`: `docker compose up -d --build web`. |
| Модель не загружается, ошибка 413 | Файл больше 512 МБ. Поднимите `client_max_body_size` в `frontend/deploy/nginx.conf` **и** `APP_MAX_MODEL_MB` в `.env` — они должны совпадать. |
| Письма не уходят, в логах `SMTP не настроен` | В `backend/.env` пустые `APP_SMTP_USERNAME`/`APP_SMTP_PASSWORD`, либо файл не подхватился. Проверьте: `docker compose exec api env \| grep SMTP`. |
| Кончилось место на диске | `du -sh data/storage/models` — скорее всего накопились старые модели. Удалите ненужные слои через интерфейс. |

Полный перезапуск, если совсем непонятно:

```bash
docker compose down
docker compose up -d --build
```

Данные при этом не теряются — они в `./data`.

## Ограничения, о которых стоит знать заранее

Это не помешает запуститься, но повлияет на планы.

* **База — SQLite, бэкенд работает в один процесс.** Это осознанно: SQLite не
  выдерживает нескольких процессов на запись. Для отдела в 10–30 человек
  ресурсов достаточно с запасом. Если пользователей станут сотни, понадобится
  переход на PostgreSQL — код на SQLAlchemy, менять придётся строку
  подключения и миграции, а не логику.
* **Один сервер — одна точка отказа.** Резервное копирование обязательно.
* **Токен входа живёт 12 часов, отзыва нет.** Уволенный сотрудник сохранит
  доступ до истечения токена, даже если удалить учётную запись. Если это
  критично — уменьшите `APP_ACCESS_TOKEN_TTL_MINUTES`.
* **Одновременное редактирование одной зоны** двумя людьми может потерять одну
  из правок (подробнее — в README, раздел 7).

## Шпаргалка по командам

```bash
cd /opt/3d-monitoring

docker compose up -d --build     # запустить / обновить
docker compose ps                # состояние
docker compose logs -f api       # смотреть логи бэкенда
docker compose restart api       # перезапустить бэкенд
docker compose down              # остановить всё
docker compose exec api sh       # зайти внутрь контейнера
```
